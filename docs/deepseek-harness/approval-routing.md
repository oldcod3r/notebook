# 审批机制：机制与策略分离

沙箱升级、危险工具调用和宿主策略都可能提出同一个问题：“这个具体操作可以继续吗？”

如果每个消费方自己弹窗、等待和记录结果，系统会出现多套取消语义、不同的无人应答行为和无法统一审计的决策。DeepSeek Harness 把审批设计成一条共享 seam：**机制定义封闭结果和路由，策略决定谁应答以及何时无需询问。**

## 审批不是一个全局回调

多会话 Agent 服务中，权限请求必须到达拥有当前 Agent 的通道。把所有请求广播给一个全局 UI，会产生严重的归属问题：用户可能在 A 会话中批准 B 会话的操作，后台 child 也可能弹出无人看到的提示。

审批请求携带发起 Agent 和具体操作，沿 waterfall 寻找应答者：

```text
consumer
  → per-session policy
  → owning channel responder
  → closed result: approved | denied | canceled
```

没有应答者时默认拒绝。一个部署没有加载 UI，不等于自动批准；无人拥有的 Agent 也不能把请求路由给任意活跃窗口。

## 机制与策略各自负责什么

| 机制 | 策略 |
|---|---|
| 请求和结果的类型 | 哪些操作自动允许或拒绝 |
| 取消与超时传播 | 当前会话是否允许询问 |
| 找到拥有者通道 | 人类、宿主还是自动控制器应答 |
| 审计事件 | 组织的风险规则 |
| 无应答时失败关闭 | 是否需要一次性批准 |

把策略硬编码进审批服务，会让 CLI、Web、ACP 和自动化宿主无法共享同一机制。把机制下放给策略，又会导致每个策略重新实现路由和取消。

## Waterfall 适合封闭决策

审批只需要一个应答者给出封闭结果。Waterfall 允许更靠近会话的策略先处理：

- 明确禁止的操作直接拒绝；
- 已有一次性授权可以直接批准；
- 需要人类判断时交给拥有通道；
- 没有任何参与者处理时失败关闭。

一旦某个监听器作出决定，后续不再继续。它与广播事件不同：审批不是收集多个观察者意见，也不能让后来的“允许”覆盖前面的强制拒绝。

## 批准结果必须封闭、可审计

消费方不应解析自由文本“看起来像同意”。结果应是有限枚举，并保留：

- 请求 id；
- 发起会话与 Agent 身份；
- 操作摘要和结构化参数；
- 决策与应答者来源；
- 取消或失效原因；
- 请求和决策时间。

模型看到的是消费方据此形成的工具结果，而不是 UI 内部对象。审计轨迹不能依赖模型是否记得复述批准过程。

## 一次性批准与策略切换不同

沙箱拒绝后的批准只允许同一操作进行一次更宽重试。它不应偷偷修改会话默认策略，也不应变成未来相似命令的永久通行证。

如果产品需要“本会话总是允许某类操作”，那是显式策略变更，应写入会话状态并向用户说明影响范围。一次性批准和持久策略使用同一个应答机制，但产生不同状态变化。

## 取消存在于多个窗口

请求可能在以下任一时刻失效：

- 进入策略前调用已取消；
- UI 正显示时父 step 被停止；
- 用户作出决定前 Agent 被释放；
- 批准后、消费方执行重试前任务已不再需要。

审批 API 必须携带调用方 signal。应答者观察取消后关闭提示；消费方在使用批准结果前再次检查自己的生命周期。批准不是对一个已经死亡操作的复活权。

## 为什么 Subagent 默认不能询问

后台 child 通常没有直接拥有者 UI。让它继承父级“可以弹窗”的审批策略，会产生悬空请求并阻塞资源清理。

进程内委派会把 child 审批策略固定为 `never`：现有权限范围内继续，越界则报告限制。需要更高权限时，由 parent 在可见通道中重新规划或创建新委派。

## 一个消费方怎样接入审批

1. 在真实危险动作之前构造结构化请求。
2. 携带确切 Agent、操作和取消信号调用共享服务。
3. 对 approved、denied、canceled 分别处理，不使用布尔值吞掉原因。
4. approved 后重新验证操作仍与请求匹配。
5. 只执行被批准的范围，不扩大参数。
6. 将执行结果与审批结果分别记录。

审批成功不代表动作成功；动作失败也不能改写“用户曾批准”的历史事实。

## 关键测试

- 无应答者时拒绝，而非挂起或允许。
- 请求只到达确切拥有者通道。
- 会话级强制拒绝能短路 UI。
- 取消会关闭等待中的提示，并阻止后续执行。
- 同一请求只能结算一次。
- 一次性批准不能用于改变后的操作。
- Child 在越界时确定性失败，不弹无人处理的提示。
- 审计记录能区分自动策略、人类应答和取消。

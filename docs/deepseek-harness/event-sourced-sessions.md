# 基于事件溯源的 Agent 会话设计

聊天应用通常把会话理解成消息数组：用户消息、助手消息、工具结果依次放进去，调用模型时直接把数组发送出去。

但 Agent 的运行过程远比聊天消息丰富。一轮执行还包含流式分片、工具调用、审批、取消、token 用量、步骤边界和持久化检查点。如果消息数组保存“对话”，另一套事件系统保存“执行过程”，两份状态迟早会出现分歧。

DeepSeek Harness 的选择是只保留一个权威事实：**Session 是一份仅追加、带类型且严格排序的事件日志；LLM 消息历史只是这份日志的派生视图。**

## 不是给消息数组补一套日志

最直观的实现通常有两条数据流：

```text
messages[]  ──→ 下一次模型请求

events[]    ──→ 调试、遥测、持久化
```

问题不在于写两次数组，而在于两个真源可能在失败路径上产生不同结果：

- 助手流已经写入部分分片，但组装消息还没有提交；
- 工具已经启动，消息数组里却还没有对应调用；
- 压缩插件改写了下次请求，却没有记录它替换了哪些历史；
- 进程在更新消息之后、写入事件之前崩溃；
- 恢复代码修补了一侧，却遗漏另一侧。

只要“当前对话是什么”由可变数组回答，而“刚才发生了什么”由事件回答，系统就必须不断证明两者仍然一致。

事件溯源把关系反过来：

```text
                  ┌─→ 调试与遥测
SessionEvent[] ───┼─→ 持久化与恢复
                  ├─→ 回放与 fork
                  └─→ deriveMessages() ─→ 下一次模型请求
```

日志不是消息变化后的旁路通知；日志本身就是状态。消息历史可以重新计算，权威事件不能被派生结果覆盖。

## 一轮执行留下哪些事件

会话日志既保存模型最终看到的内容，也保存解释这些内容如何产生的执行证据。可以把事件粗略分成四组：

| 事件角色 | 典型内容 | 是否进入模型历史 |
|---|---|---|
| 轮次与步骤边界 | `turn/start`、`step/start`、`step/end`、`turn/end` | 否 |
| 模型输入与完成消息 | `user/message`、`assistant/message`、`context/message` | 是 |
| 流式与计量证据 | `assistant/chunk`、token 用量、错误 | 否 |
| 工具过程 | `tool/call`、`tool/result` | 只有形成消息语义的结果进入 |

这里最值得注意的是 `assistant/chunk` 和 `assistant/message` 同时存在。

原始分片保留 token 级别的流式证据；模型流结束后，系统再追加一条组装完成的 `assistant/message`。后者是派生消息历史的权威锚点，并通过 `sourceEventSeqs` 引用生成它的全部分片。

于是系统同时获得两种能力：

- UI 或诊断工具可以回放原始流；
- 下一次模型请求不必重新猜测分片应如何组装。

如果一次成功的模型调用没有输出任何分片，完成锚点仍然存在，并用空来源列表表达“已知是空流”，而不是让“没有记录”同时表示多种状态。

## 顺序不是实现细节，而是协议

事件日志能否回放，取决于同一动作在任何运行中都留下相同的相对顺序。DeepSeek Harness 把一次 step 的关键顺序固定为：

```text
领取 inbox 消息
  → agent/pre-step
  → step/start
  → user/message
  → 派生模型请求
  → assistant/chunk × N
  → assistant/message
  → 分派 tool/call
  → tool/result
  → step/end
```

几个顺序约束尤其重要：

1. **先决定是否进入 step，再记录 `step/start`。** 否则被策略拦截的空步骤也会污染日志。
2. **先追加本轮用户消息，再派生模型请求。** 持久日志因此能重建模型实际收到的输入。
3. **先提交完整 `assistant/message`，再分派工具。** 工具执行时遵循的调用内容已经成为日志中的稳定事实。
4. **工具调用和结果必须闭合。** 恢复后的提供方 transcript 不能留下一个永远等不到结果的调用。

这类约束应由回归测试固定。依赖某个函数当前恰好先调用 A 再调用 B，在重构后非常容易悄悄改变回放语义。

## Surface：不改日志，也能改变下一次上下文

仅追加日志遇到一个现实问题：长会话需要压缩，工具结果也可能需要裁剪。既然旧事件不能改写，怎样让后续模型不再看到某段历史？

DeepSeek Harness 在原始日志之上维护一层 **surface**：它是所有“可产生模型消息的事件”的有序投影。

每个进入 surface 的事件携带两类元数据：

```ts
type SurfaceOp =
  | "append"
  | { op: "replace"; start: number; end: number };

interface SurfaceMetadata {
  surfaceOp: SurfaceOp;
  sourceEventSeqs?: number[];
}
```

`append` 把新消息放到投影尾部。`replace` 则遮蔽 surface 中一段连续范围，并把当前事件放到原位置；被遮蔽事件仍完整保留在原始日志中。

例如，压缩引擎可以追加一条摘要消息：

```text
原始日志：  [用户 A] [助手 B] [工具 C] [用户 D] [摘要 S]
surface：   [摘要 S]                    [用户 D]
```

摘要事件通过 `replace(start, end)` 说明替换范围，通过 `sourceEventSeqs` 列出被遮蔽的来源。回放时不需要重新运行压缩模型，也不需要依赖监听器顺序；同一份日志可以确定性地还原当时使用的上下文。

### 为什么不是每个插件都包装模型请求

让压缩、上下文注入和结果裁剪插件依次修改 `agent/request` 看起来更灵活，但会产生三个问题：

- 最终结果取决于监听器注册顺序；
- 修改只存在于当次内存调用，无法持久回放；
- 每增加一种历史操作，核心派生逻辑都要理解一个新插件。

Surface 把所有历史操作压缩成 `append` 和 `replace` 两种可验证动作。插件决定替换什么，Session 负责验证范围、来源和顺序。

## 持久化不应该拖慢事件热路径

“日志是唯一真源”不等于每次追加都同步 `fsync`。

内存中的事件追加和 `session/event` 通知保持同步，因此本轮后续逻辑立即看到确定顺序。持久化后端订阅事件并延后写入，在语义检查点通过 `session/flush` 等待排空。

这个拆分同时满足两种需求：

| 热路径 | 持久边界 |
|---|---|
| 追加事件不等待磁盘 I/O | 在模型请求、工具执行和轮次结束等边界确认日志已落盘 |
| Agent 可以继续组装和调度 | 崩溃恢复不会越过尚未持久化的关键动作 |

持久化接口直接读写 `SessionEvent`，而不是再定义一套“持久化消息”结构。JSONL 可以把连续分片压成更紧凑的物理记录，SQLite 可以把事件映射成数据行，但逻辑读取后必须恢复相同、连续且无损的事件序列。

## 崩溃恢复：关闭未完成的轮次，而不是截断

Agent 的一次 step 可能运行很久。进程崩溃时，日志尾部可能已经包含有效的助手输出和工具工作，只是还没有写下完整的结束边界。

一个简单策略是回退到最后一个完整 `turn/end`，但这会静默删除中间所有真实工作。DeepSeek Harness 选择保留连续、可解析的事件，并在恢复视图中补齐必要的闭合事件：

- 为没有结果的工具调用生成按风险分类的错误结果；
- 补上缺失的 `step/end`；
- 以 `kind: "interrupted"` 结束未完成轮次。

只有最后一条物理记录本身写了一半时，才丢弃这条不完整尾记录。更早位置的解析错误或序号空洞属于数据损坏，必须拒绝加载，而不是猜测修复。

这背后的原则是：**恢复可以补充“执行已经中断”的事实，但不能伪造“执行从未发生”。**

## 回放和 fork 为什么会自然出现

当日志是完整状态时，回放就是用已有事件创建 Session；消息、surface 和运行上下文都从同一序列重新派生。

Fork 也不需要复制可变对象的内部状态。它选择一段合法的事件种子，创建新的会话身份，再从种子恢复投影。父会话继续保持原样，子会话获得确定的起点。

这与 [pi 的会话存储](/pi/sessions) 有一个重要区别：

| pi | DeepSeek Harness |
|---|---|
| 每条记录通过 `parentId` 组成可切换的分支树 | 每个 Session 内是按 `seq` 排序的线性事件日志 |
| 当前上下文由 `leafId` 沿父链回溯 | 当前上下文由 surface 投影派生 |
| 分支可以共存于同一会话文件 | fork 创建具有自身身份的新会话 |
| 压缩条目改变当前路径的上下文构建 | replace 操作遮蔽 surface 范围，原事件仍留在日志 |

两者都坚持 append-only，但解决“当前上下文是什么”的方式不同：一个依赖树路径，一个依赖日志投影。

## 这套设计付出了什么

事件溯源并不会自动让系统更简单。它把复杂度从“维护多个状态”转移到了“维护一份严格的事件协议”：

- 事件类型和顺序需要兼容性约束；
- 每条引用必须指向已知且更早的事件；
- surface 替换必须完整覆盖被遮蔽节点；
- 派生成本会随历史增长，需要增量缓存和上下文压缩；
- 持久化格式必须保留连续序号和事件保真度；
- 恢复逻辑必须区分可闭合的中断与不可接受的数据损坏。

它换来的收益是让追踪、恢复、回放和模型上下文不再各自解释一份不同的历史。

## 在自己的 Agent 中落地

不必一开始实现完整 surface。最小可行路径可以分成四步。

### 第一步：确立唯一真源

- 所有会影响后续行为的事实先写事件，再更新派生视图。
- 消息数组只能是缓存，必须能从事件重新构建。
- 为事件分配连续序号，拒绝重复或空洞。

### 第二步：固定顺序协议

- 明确用户消息、助手完成消息、工具调用和工具结果的相对顺序。
- 为取消、超时、空响应和异常分别建立闭合路径。
- 用回归测试比较完整事件序列，而不只断言最终文本。

### 第三步：分离热路径与持久边界

- 内存追加保持同步和便宜。
- 持久化采用 write-behind，但在有业务意义的边界提供 awaited flush。
- 冷加载严格校验格式、序号和引用，不静默跳过损坏。

### 第四步：再引入可回放投影

- 历史操作以日志中的声明式事件表达。
- 替换只遮蔽派生视图，不删除原始事实。
- 记录来源关系，使回放可以验证替换覆盖范围。

判断设计是否成立，可以做一个简单实验：清空所有运行时缓存，只保留持久事件，再加载一次。如果系统不能得到相同的模型历史和可恢复状态，就仍然存在第二个隐藏真源。

# Agent Note：用决策生命周期管理技术知识

代码告诉我们系统现在怎样工作，提交历史告诉我们它怎样变成今天这样，但它们通常回答不了两个更重要的问题：**为什么选择这条路，以及当时放弃了什么。**

DeepSeek Harness 用 Agent Note 保存这部分知识。它像 ADR，但多了一层很实用的设计：决策记录不是写完就永久躺在同一个目录，而是拥有可检查的生命周期。

## Agent Note 与 ADR 有什么不同

Agent Note 没有发明一种全新的设计文档。它沿用了 ADR 保存架构决策及其理由的核心思想，但把“决策之后怎么办”变成了一套显式约定。

| 维度 | 常见 ADR 实践 | Agent Note |
|---|---|---|
| 状态 | proposed、accepted、deprecated 等，通常写在文档内 | 状态同时编码在目录和文档头部 |
| 实施后维护 | 经常作为决策时点的历史快照 | 与当前实现中的路径、名称和结构保持同步 |
| 未采用方案 | 可能记录，也可能省略 | 必须记录真实备选方案及其落选原因 |
| 被否决方案 | 通常留在同一组记录中 | 只有仍能阻止诱人错误的记录才保留 |
| 归档 | 多由团队自行约定 | 只有 implemented 可以归档，归档后冻结 |
| 自动检查 | 主要依赖模板和评审 | 检查状态、目录、章节、链接及文档配对 |

真正的差异不是名字，而是把设计文档当作一组持续演进、可以清理、也可以机械验证的知识资产。

## 文档真正要保存的是决策差异

一份有价值的设计记录，不应该只是实现说明。函数名、目录结构和配置字段可以从源码找到，重复抄一遍只会制造第二份容易过期的事实。

真正容易丢失的是决策发生时的差异：

- 当时的问题是什么，不采用任何方案会怎样？
- 最终方案建立了哪些必须长期成立的约束？
- 还有哪些看起来合理的方案，为什么没有采用？
- 选择带来了什么收益，又主动接受了什么代价？

因此，Agent Note 的基本结构不是“背景、实现步骤、完成情况”，而是问题、决策或提案、备选方案，以及后果或风险。它迫使作者写下决策击败了什么，而不只是宣布一个结果。

## 一个真实例子：为什么会话日志必须是唯一真源

“事件溯源的会话”这项决策展示了 Agent Note 与普通实现文档的区别。

它面对的问题不是“怎样实现 `Session` 类”，而是 Agent 运行时同时需要严格追踪、完整回放、会话 fork 和异步持久化。如果可变消息数组负责当前状态、事件只负责通知，两份数据就可能分歧。

最终决策是让仅追加的类型化事件日志成为唯一真源，LLM 消息历史由日志派生。工具调用前后的消息顺序、原始流分片、轮次结束时的持久化检查点，都围绕这条约束建立。

这份记录最有价值的部分并不是列出接口，而是保存了被放弃的直观方案：

> 使用“可变消息数组 + 事件通知”会更简单，但状态与日志可能分歧；让日志本身成为状态，才能从结构上消除分歧。

几年后，即使 `Session` 的文件位置和接口名称变化，这个取舍仍能回答一个关键问题：为什么不能为了少写一些派生逻辑，重新引入独立的可变消息真源。

## 用目录表达生命周期

每份记录的路径同时编码状态和类别：

```text
{lifecycle}/{class}/yyyy-mm-dd-topic-title.md
```

生命周期分为四种，合法转换只有三条：

| 从 | 到 | 含义 |
|---|---|---|
| `proposed` | `implemented` | 方案已经交付，计划改写为当前事实 |
| `proposed` | `rejected` | 方案未采用，保留仍有价值的否决理由 |
| `implemented` | `archived` | 决策已经完成，理由不再指导日常修改 |

`rejected` 不进入归档；失去护栏价值时直接删除。`proposed` 也不能归档，因为尚未交付的方案不存在“已完成但不再活跃”的状态。

### proposed：等待验证的方案

提案描述准备做什么，而不是把未来计划写成当前事实。它需要给出验收标准和风险，让评审者知道什么状态算完成，以及失败可能发生在哪里。

提案过时后也不应被归档。归档意味着一项已经交付的决策失去日常指导价值；尚未实施的方案只有两个合理结果：继续保留，或者诚实地转为 rejected。

### implemented：与当前系统保持同步的决策

进入 implemented 不是简单地改一行状态。计划必须改写为已经交付的现实：`Proposal` 变成 `Decision`，验收条件变成实际验证，风险则沉淀为已经接受的后果。

这里有一个容易忽略的要求：实现记录不是不可修改的历史快照。代码移动、包重命名、配置键变化时，记录中的事实也要同步更新；但决策本身不能被悄悄改写成另一个决策。新的选择应当拥有新的记录，并与旧记录建立替代关系。

### rejected：保留仍然诱人的错误

不是每个失败提案都值得永久保存。Rejected Note 的价值在于阻止团队再次走进一个**仍然看起来合理、但已经证明代价更高**的方向。

如果一个方案已经不可能重现、被后续设计彻底吸收，或者不再能避免有意义的误判，删除往往比保留更好。知识库不是墓地；噪声越多，真正的护栏越难被发现。

### archived：冻结已经完成历史使命的记录

一项 implemented 决策已经完全落地，而且其中的理由不太可能再指导未来修改时，可以进入 archived。归档内容被冻结，不再跟随当前代码更新，也不能被当作当前行为的权威来源。

这个边界很关键：

- `implemented` 回答“当前为什么如此”，需要维护；
- `archived` 回答“过去为什么曾经如此”，需要冻结。

## 分类应描述决策性质

DeepSeek Harness 将记录分成六类：

| 类别 | 关心的问题 |
|---|---|
| `feature` | 新增了什么用户或模型能力 |
| `bug-fix` | 哪个缺陷或事故缺口被修正 |
| `simplification` | 在不增加能力时移除了什么 |
| `architecture` | 交付源码内部的结构和运行时词汇 |
| `process` | 源码周边的工具、策略和工作流 |
| `testing` | 测试基础设施与验证策略 |

这里最有启发的是 `architecture` 与 `process` 的分界：前者属于交付系统本身，后者属于围绕系统工作的方式。分类不是为了让目录更漂亮，而是让读者在进入文档之前就知道这项决策影响哪个层面。

## 为什么不用一份集中索引

项目不维护手写总索引：生命周期目录本身就是工作清单，文件名可以搜索，链接可以机械检查。集中索引会引入额外真源，每次新增、移动或归档都要同步维护，规模增长后很容易先于内容过期。

面向读者的内容地图仍然有价值，但它应是编辑后的阅读入口，而不是决策状态的权威数据库。

## 让规则可以被机器检查

仅靠写作约定很难长期维持一致。Agent Note 把一部分语义压缩成可机械验证的形式：

- 状态必须与所在目录匹配；
- 不同状态必须包含对应章节；
- 每份记录必须讨论真实的备选方案；
- 中英文记录必须成对并保持结构一致；
- 归档记录必须完整冻结；
- 相对链接和类别集合由门禁检查。

机器不能判断理由是否深刻，却可以消灭大量结构性退化，把人工评审留给真正需要判断的部分。

## 在自己的项目中落地

不必一开始复制全部规则。一个足够实用的最小版本可以是：

```text
decisions/
├── proposed/
├── implemented/
├── rejected/
└── archived/
```

每份记录只强制五件事：

1. 描述不依赖解决方案也能成立的问题。
2. 明确当前状态，不把计划写成事实。
3. 写出至少一个真实考虑过的替代方案及落选原因。
4. 记录收益与代价，而不只记录收益。
5. 当决策被替代时，建立双向链接并重新判断旧记录的状态。

随后再根据痛点增加门禁：先检查状态与目录，再检查必需章节，最后才考虑双语配对、冻结清单或引用完整性。

### proposed 最小模板

```md
# Decision: <标题>

Status: proposed

## Problem

不依赖具体方案，描述需要解决的问题及不处理的后果。

## Proposal

描述准备建立的约束和可观察行为。

## Alternatives considered

- **方案 A**：为什么没有采用。
- **方案 B**：为什么没有采用。

## Acceptance criteria

- 什么可观察状态表示方案已经完成。

## Risks

- 可能失败的地方，以及主动放弃的能力。
```

### implemented 最小模板

```md
# Decision: <标题>

Status: implemented

## Problem

描述这项决策所解决的问题。

## Decision

使用现在时描述已经交付的约束和行为。

## Alternatives considered

- **方案 A**：为什么没有采用。
- **方案 B**：为什么没有采用。

## Consequences

- 获得了什么。
- 付出了什么代价。
```

从 proposed 转为 implemented 时，不要只修改状态行。计划、验收条件和风险也要分别改写为当前决策、验证事实与实际后果。

## 最重要的取舍

Agent Note 方法增加了写作和维护成本。每个非平凡变更都要求解释理由，implemented 记录还要跟随代码事实演进。这不是免费的。

它换来的是另一种效率：新成员不必从提交记录和评审聊天中考古；同一个诱人方案不会每隔几个月被重新争论；Agent 在修改代码时也能检索到源码无法表达的边界。

判断一份记录是否值得存在，可以用一个简单问题：

> 如果只保留代码，半年后的人是否仍能理解为什么必须这样设计？

如果答案是否定的，这部分差异就值得写进决策记录；如果代码已经说明了一切，就让文档保持沉默。

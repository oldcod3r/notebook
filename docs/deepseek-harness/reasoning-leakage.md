# 清理工程文档中的推理过程泄漏

工程文档最常见的噪声，不一定是啰嗦，而是采用了错误的观察视角：文字在复述作者当时如何思考、PR 如何演进、评审者提出过什么，而不是说明仓库当前可验证的事实。

这类内容可以称为推理过程泄漏。它不会暴露模型的“秘密思维”，但会把一次性会话上下文泄漏到长期维护表面。

## 一个判断问题就够了

对每个可疑段落问：

> 只看到当前仓库、看不到会话记录、PR 讨论和未提交设计稿的读者，能否解析每个引用并验证每个事实？

如果不能，就把仍然有效的事实改写成仓库当前视角，再删除周围的过程记录。若整段没有有效事实，例如孤立的“审计项 C2”，可以直接删除。

这个判断强调的是可解析性，而不是禁止历史。事故复盘和设计记录本来就需要历史证据；README、JSDoc 和普通注释则通常只应描述当前行为。

## 八类高频泄漏

### 1. 无法解析的设计引用

```text
泄漏：注册表拒绝重名（decision 7：名称是扁平的）。
改写：注册表拒绝重名；名称是扁平的，不支持命名空间。
```

如果决定已有提交到仓库的权威文档，就改成可点击的文档名称和路径；如果没有，保留事实，删除编号。

### 2. PR 与提交视角

“这个 PR 增加……”“后续栈中的 PR 会……”会在合并后立刻失效。应写当前机制或扩展点：

```text
泄漏：后续 PR 会增加远程后端。
改写：远程后端可以实现该接口，无需修改渲染层。
```

真正待办的工作进入带所有者的 TODO 或 issue。

### 3. 变更叙事和版本戳

“以前”“不再”“当前版本”“这一次改动”要求读者了解仓库考古。普通文档应写现在的行为。

修复过的回归仍有价值，但应改为当前反事实：

```text
泄漏：这里以前会重复编码多字节标签。
改写：缺少字节长度保护时，多字节标签会被重复编码。
```

### 4. 评审过程

“评审中否决”“reviewer 已确认”“第 5 版设计”都不是长期理由。设计记录可以保留备选方案及其技术后果，但不需要保留谁在第几轮说过。

### 5. 面向评审者的自证

```text
泄漏：这个类型转换是安全的，因为 SDK 只是没有把可选字段声明得足够严格。
改写：SDK 创建的对象会填充所有可选字段；其声明类型比运行时保证更宽。
```

维护者需要不变量，不需要作者对质疑的回应。如果代码已明显表达不变量，整条注释都可以删除。

### 6. 控制流和推导旁白

“首先归一化，然后截断，最后包装”只是复述下面三行代码。测试中的“创建会话、发送消息、等待结果”同样如此。

只保留非显然理由，例如：

> 两轮交互必须恰好产生四条日志；投影会去重共享前缀。

### 7. 含糊的计划残留

“暂时应该够用”“可能没问题”既无法验证，也没有责任人。要么删除，要么写成有依据的边界和失败行为：

> 64 KiB 覆盖已观察到的最大帧 48 KiB；更大的帧会在 `decode` 明确失败。

真正延期的工作使用可检索的 TODO 或 issue。

### 8. 写作过程中的语言残片

中英文混杂的工作词、分隔符和“见设计稿”等临时指针需要翻译或改成可解析的外部引用。外部标准章节、Figma frame 名等稳定标识可以保留。

## 搜索词只是探针，不是判决器

可以用 `rg` 搜索 `this PR`、`used to`、`for now`、`reviewer`、`decision N`、`设计稿`、`上一轮`、`旧版` 等词快速提高召回率，但每个命中都需要语义判断。

常见合法命中包括：

- “用于签名请求的 key”中的 `used to` 是用途，不是过去时；
- “旧连接排空后新连接才接收”描述运行时对象；
- `/v1/chat` 是协议标识，不是临时版本戳；
- RFC 的章节编号和已提交文档的锚点可以解析；
- lint suppression 的理由是必需文字，理由错误时应修正而非删除；
- “测得 512 层约 0.15 秒”中的测量来源是调整上限的重要依据。

模式搜索一定会漏掉没有关键词的过程叙述。因此还要人工阅读范围内最密集的 README、模块注释和设计记录。

## 删除前先防止过度修正

最危险的清理不是少删，而是把事实一起删掉。

### 不要改变模态

```text
原文：这些直接注册是等待迁移到 slot 的例外。
错误：这些直接注册是允许的例外。
```

“等待迁移”是一项义务，“允许”却把现状合法化。

### 不要把假设写成已交付

删除“未来”可能把设计示例变成当前事实。更准确的写法是：

> 一个假设的 IPC shell（当前并不存在）可以继承 executor 并覆盖 `spawn`。

### 不要丢失数字的来源

“测得最大模块为 3.1 MiB，因此上限为 4 MiB”中的“测得”说明数字来自观察，而不是定义。去掉它会让下一位维护者不知道何时需要重新测量。

### 按命题删，不按整句删

一句话可能一半是旁白，一半是重要耦合：

```text
原文：通知会复述检查顺序；通知文本也是 verify-doc-typecheck 的编译输入。
改写：通知文本是 verify-doc-typecheck 的编译输入。
```

## 一套可重复的清理流程

```text
确定范围与排除项
  → 模式搜索提高召回率
  → 无关键词阅读高密度文字
  → 为每段枚举有效命题
  → 改写为当前仓库视角
  → 更新文字所有者及派生产物
  → 复跑搜索与文档门禁
```

生成目录应修改源 JSDoc 后再生成；双语文档应同步语义；模型可见字符串的改写则必须配套快照或行为测试。冻结历史、录制 fixture 和快照通常保留原始声音，不应纳入普通清理。

## 审查清单

- 每个内部引用都能从当前仓库或明确的外部来源解析。
- README、JSDoc 和注释不采用某个 PR 或评审轮次的视角。
- 当前行为替代了“以前/现在”的仓库考古叙事。
- 评审者身份被删除，技术不变量和取舍仍然保留。
- 控制流和测试步骤没有被注释重复。
- 含糊延期改成有所有者的 TODO、issue 或可测边界。
- 清理前逐项枚举命题，没有改变义务、例外和事实状态。
- 合法的 issue、标准、测量和 suppression 理由没有被误删。
- 可见文字、生成文档和双语页面完成对应验证。

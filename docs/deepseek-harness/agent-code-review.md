# 面向 Agent 项目的代码审查

传统业务代码审查常把注意力放在输入、输出和数据一致性上。Agent 系统还多出一组容易被普通 diff 隐藏的问题：模型看到的内容、工具真正执行的权限、异步任务的所有权、取消后的副作用，以及会话恢复时能否重建同一个世界。

因此，Agent 项目的审查重点不是收集更多样式问题，而是沿真实执行链找到那些“单元测试绿了，产品仍可能失效”的缺口。

## 先确认你审查的到底是什么

审查开始前需要固定三件事：实时 base、精确 head、完整变化范围。PR 可能重定向 base、合并父分支或包含未预期的堆叠改动；只看网页上最显眼的文件容易审错范围。

建议先得到一个变化地图：

```text
接口与类型
  → 实现与注册
  → 配置与真实入口
  → 模型可见表面
  → 持久化和生命周期
  → 测试、文档与生成物
```

然后阅读足够的周边代码和当前消费者。diff 告诉你改了什么，周边代码才告诉你破坏了什么。

## 按风险排序，而不是按文件顺序

优先级通常应是：

1. 正确性与必需行为；
2. 权限、安全边界和绕过路径；
3. 生命周期、并发、取消与资源释放；
4. 持久化、恢复和派生状态一致性；
5. 模型可见契约与真实入口；
6. 测试证据和文档同步；
7. 可读性与样式建议。

一个有证据的阻断问题，比十条命名建议更有价值。已经由绿色门禁可靠阻止的问题，也无需重复报告。

## 追踪接口的两侧

每个接口变更都要同时检查生产者和消费者：

- 返回值差异和错误是否被调用者完整处理；
- 取消信号是否真正传到执行资源；
- 谁拥有任务、进程、监听器和持久状态；
- dispose 返回时是“已请求停止”还是“完全静止”；
- 新公共方法是否只有一个内部消费者。

最后一种情况常暴露抽象泄漏：为了一个插件，给通用 session 或 registry 增加公共能力。更小的设计可能是在构造时向该消费者传入私有 capability closure，而不是扩大所有调用者都能看到的 API。

## 生命周期审查要画出时间线

异步 setup、callback、子进程和 teardown 不适合只按代码行阅读。至少要检查这些竞态：

```text
创建资源 → 首次 await → 发布给外部 → 正常运行 → 请求取消 → 完全释放
```

在每个边界问：

- 发布前取消会不会泄漏尚未登记的资源？
- await 期间失败由谁观察，是否形成未处理 rejection？
- callback 抛错会不会逃出宿主边界？
- 外部重入前，所有权是否已经确定？
- listener、timer、subscription 和子进程是否全部解绑？
- dispose 是否等待后台 worker 和输出流停止？
- 取消后是否仍可能发生写文件、发消息或扣费？

这类问题需要测试“取消前、发布中、完成后”等多个时点，而不是只测 happy path 上的一次 abort。

## 权限审查必须走到最终操作

prompt 中写“不要访问网络”不构成安全边界，工具 schema 的校验也不等于执行层阻断。

对每条拒绝路径，要一直追踪到最终副作用：

```text
模型请求
  → 工具路由
  → 策略/审批
  → wrapper 或 facade
  → 实际文件、进程、网络操作
```

同时寻找旁路：直接调用、备用工具、插件监听器、旧 facade、恢复后的任务、worker 或 subprocess。安全断言应证明被拒绝的操作没有发生，而不只是 UI 出现了“已拒绝”。

还要检查默认值与公开选项是否有真实消费者依据。把某个外部产品的概念直接做成公共枚举，可能无意间把 provider 特性扩散成核心模型。

## 从模型视角审查

Agent 的实际接口不仅是 TypeScript 类型，还包括模型看到的：

- system prompt 和动态上下文；
- 工具名称、描述和 schema；
- 工具结果、错误和 stop reason；
- 会话恢复后重放的消息；
- 编辑器、终端和 ACP 客户端呈现的文本。

审查时要看最终渲染内容，而不是只看字符串模板。模型不需要知道内部任务 ID、provider 装配细节或实现阶段；但必须知道可执行操作、限制和恢复方法。

稳定文字应由快照逐字约束，动态行为应通过真实路径测试。expected-output diff 是行为变更，不应当作格式噪声一键接受。

## 持久化与派生状态要找权威来源

Agent 系统会同时维护事件日志、缓存、prompt 投影、UI 回显和查询视图。对每个保留值要判断它是借用还是拥有，并追踪：

- 写入成功点在哪里；
- 通知是在提交前还是提交后发出；
- reload、late loading 或热更新后如何重建；
- fork 是否复制历史而不是复制派生缓存；
- 回放时是否会重复触发外部副作用；
- 失败后哪个状态仍被视为权威。

只验证内存中的当前实例不够。持久化不变量应在重载后仍成立，并包含一个故意无效的 negative control，证明检查器确实会失败。

## 边界必须覆盖最终产物

长度、token 和字节限制经常只作用于中间片段，随后又被 wrapper、metadata 或编码放大。审查上限时要找到最终拥有完整结果的组件，并覆盖：

- 极小和恰好等于上限；
- 单个超大 chunk；
- 多 chunk 合并后超限；
- 多字节文本的字节长度；
- 错误信息自身是否又突破限制。

限制应约束最终发送或持久化的值，而不是某个看似接近的局部变量。

## 测试证据要覆盖真实入口

手工 mount 一个插件，不能证明 Loader 能加载它；直接调用 adapter，不能证明 bin、worker、ACP bridge 或 subprocess 能工作。

有效的证据通常分层：

| 层级 | 证明什么 |
|---|---|
| 单元测试 | 分支、不变量和错误语义 |
| 集成测试 | 注册、装配、事件与持久化协作 |
| 构建产物 smoke | export、loader、bin 和 worker 入口 |
| 无密钥产品测试 | 官方产品配置、协议和进程生命周期 |
| 真实 API E2E | provider、传输和真实模型服务 |

测试断言应观察外部结果、事件、日志和资源释放，而不是复述实现字段，更不能相信 Agent 自己报告“已经完成”。覆盖率证明代码被执行，不证明场景断言正确。

## 文档和代码必须在同一变更中对齐

配置、默认值、错误、事件和公开行为改变时，相应 README 与 JSDoc 应同步。注释只写非显然契约，设计记录则在功能落地后改成当前时态，并保留验证层级和明确的覆盖缺口。

模型可见文字、双语文档和生成目录还要检查各自的 owner 与同步流程。自动门禁能发现断链和未生成文件，却不能证明两种语言语义一致，也不能证明文档描述了真实代码。

## 如何写一条可执行的审查意见

一条有效 finding 包含四部分：

```text
缺陷：什么契约被破坏
位置：最小且准确的代码范围
影响：用户、模型或资源会看到什么结果
证据：哪条执行路径、竞态或反例可以触发
```

例如：

> `dispose()` 只触发 AbortController，没有等待 provider promise。调用者在 dispose 返回后会释放 session，但后台任务仍可写入该 session。测试可以让 provider 在收到 abort 后延迟一次写入，断言 dispose 必须等到写入路径静止。

局部缺陷放在最紧的代码行；跨模块的所有权或架构问题放在整体评论。阻断问题与建议分开，避免用“我同意”“看起来可以”代替技术证据。

## 审查清单

- 已确认实时 base、精确 head 和完整变化范围。
- 每个新接口都追踪了生产者、所有当前消费者和错误分支。
- 异步资源检查了发布前取消、await 失败、重入和静止销毁。
- 权限拒绝一直落实到最终副作用，并覆盖旁路调用。
- prompt、工具 schema、结果和诊断按模型最终所见审查。
- 事件、缓存、投影和重放指向明确的权威状态。
- 限制覆盖最终产物、exact limit 和多字节输入。
- 测试包含真实 loader、bin、worker、bridge 或进程入口。
- 断言观察外部结果，并有能失败的 negative control。
- README、JSDoc、设计记录、生成物和双语文档与代码一致。
- finding 说明缺陷、位置、影响和可复现证据。

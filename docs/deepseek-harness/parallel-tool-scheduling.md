# 工具调用的安全并行调度

一条 assistant 消息可以同时发出多个工具调用。如果它请求读取三个互不相关的文件，串行执行只会叠加延迟；但如果两个调用都修改同一资源，盲目并行又会制造竞态。

调度器无法仅凭工具名称证明安全。DeepSeek Harness 把判断放回最了解语义的一方：**工具针对已经解析的本次参数，声明该调用是否能与其他同样安全的调用重叠。**

## 并发是宿主调度，不是模型参数

模型只表达“这些调用属于同一批”。是否并行属于宿主执行策略，不应出现在工具 JSON Schema 中，也不应要求模型正确填写 `parallel: true`。

工具可以提供一个同步纯函数：

```ts
isConcurrencySafe(args): boolean
```

只有明确返回 `true` 的调用才进入共享批次。分类器缺失、参数无效、抛错或返回其他值，都按独占调用处理。

默认独占很重要：新增工具如果忘记分类，不会意外获得并发副作用。

## 为什么分类器是一元函数

更强的接口可以比较同批两个调用：路径不同的写入并行，路径相同的写入串行。但这会把调度问题变成成对相容性图，调用数量增加后组合复杂度迅速上升。

一元约定更简单：返回 true 意味着“我可以和任何同样返回 true 的同级调用重叠”。它能表达常见的输入敏感规则：

```text
read(path)   → true
write(path)  → false
```

它不能表达“两个 write 只有路径不同时才安全”。这种需要调用间关系的操作继续独占，是刻意接受的能力边界。

## 滚动池与独占屏障

调度器按模型顺序扫描调用：

- 并发安全调用进入有界滚动池；
- 独占调用先等待前面的池排空，再单独执行；
- 独占完成后，后续安全调用重新组成池。

```text
safe A ─┐
safe B ─┼─ parallel pool ─┐
safe C ─┘                 ├─ drain
exclusive D ──────────────┘─ run alone
safe E ─┐
safe F ─┴─ next pool
```

并发上限控制同时未结算的工具数量，防止单条模型消息制造无限 fan-out。

## 完成顺序与提交顺序分离

并行调用可能乱序完成，但模型历史必须保持原始调用顺序。否则同一条 assistant 消息在不同机器或网络延迟下会派生出不同 transcript，回放和缓存都会失去确定性。

调度器可以实时展示每张工具卡的进度，但只有前面的调用都可提交时，才按原顺序追加结果：

```text
完成时间：B → C → A
提交历史：A → B → C
```

代价是快速的 B 可能等待缓慢的 A，收益是模型观察顺序稳定。

## 日志必须为每个已启动调用闭合结果

并发不会放松事件协议。每个实际启动的调用都要有 `tool/call` 和终态结果；取消时，尚未分发的调用也需要合成明确的 aborted 结果，不能留下孤立调用。

结果顺序按模型调用顺序提交，而不是按完成时间写入模型 surface。诊断事件仍可以记录真实开始和结束时间。

## Subagent 为什么可以声明并发安全

Subagent 可能修改共享工作区，看起来不应无条件并行。但后台和可继续委派本来就能与后续工作重叠，只有前台形态被串行并没有真正保护资源。

Subagent 工具自身满足调度器关心的结构性约定：

- 每个 child 在独立 Session 中工作；
- 启动状态、取消和结算彼此隔离；
- 父会话只由循环按顺序提交结果；
- 后台注册是同步、可交换的任务插入。

共享工作区效果仍由模型协调。这是一项产品风险，而不是父会话状态安全问题。`maxParallelToolCalls` 限制前台 child；返回 id 后继续运行的后台 child 还需要自己的容量限制。

## 分类器的编写原则

适合返回 true：

- 只读查询；
- 独立网络读取；
- 操作状态完全封装在每次调用内部；
- 只向并发安全注册表做可交换插入。

应保持独占：

- 修改共享配置或工作区；
- 依赖上一个调用副作用；
- 使用单一全局游标或不可重入客户端；
- 需要调用间路径比较才能证明安全；
- 无法解释并发失败如何隔离。

分类器必须同步且纯，只检查已解析参数，不执行 I/O，不读取会变化的外部状态。调度阶段的“检查”不能自己成为副作用来源。

## 测试并发不能只测耗时

可靠测试应使用门控：两个调用都必须先到达阻塞点，测试才同时释放它们。若任一隐藏串行化存在，测试会死锁或超时，而不是因为机器偶然很快而误判。

还要验证：

- 完成乱序但结果提交有序；
- 独占调用确实排空前后池；
- 一个调用失败不取消无关同级；
- 取消能闭合所有已发布调用；
- 并发上限不会被后台返回 id 绕成无限活动任务。

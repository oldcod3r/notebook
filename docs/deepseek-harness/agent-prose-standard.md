# Agent 工程中的文档写作方法

Agent 项目的文字会直接参与系统行为：提示词影响模型，工具描述影响调用选择，诊断信息影响恢复路径，注释和设计记录则决定维护者是否会破坏隐藏契约。

因此，好的工程文档不是“写得更多”或“写得更短”，而是把代码无法独立表达、但调用者和维护者必须知道的事实留在正确位置。

## 写作对象是契约，不是实现过程

一段工程文字至少可能承载以下事实：

- 谁在什么条件下执行什么动作；
- 动作发生的时机和顺序；
- 调用者必须、可以或绝不能做什么；
- 资源由谁拥有，何时转移所有权；
- 失败如何暴露，取消是否意味着完全停稳；
- 哪些副作用会持久化，哪些状态只能临时观察。

编辑时应先列出这些命题，再删重复、装饰和推导过程。字数减少不是目标，命题完整且更容易验证才是目标。

例如：

> 协调器序列化持久化。

这句话太短。它没有说明序列化范围、销毁顺序和错误去向。更完整的表达是：

> 协调器按会话串行写入；销毁完成前会刷新缓冲事件，并把后端失败返回给调用者。

后一句虽然更长，却能直接约束实现和测试。

## 不同位置需要不同的信息密度

同一个事实不应原样复制到所有地方。每种文字表面服务不同读者：

| 位置 | 应保留的内容 | 应删除的内容 |
|---|---|---|
| 公共 JSDoc | 返回值差异、异常、副作用、所有权、时机、取消和持久性 | 私有状态机的逐分支讲解 |
| 内部注释 | 非局部不变量、竞态顺序、安全边界、意外失败行为 | 对下一行代码的复述 |
| 模块说明 | 模块职责、依赖、生命周期和关键架构选择 | 文件内类与函数目录 |
| 测试注释 | fixture 或间接断言为何必要、回归由什么外部现象证明 | arrange/act/assert 的逐步旁白 |
| README | 配置、语义、失败、限制、扩展点和用户可见效果 | 普通清理任务和实现库存 |
| 设计记录 | 决策、备选方案、后果、验证证据和明确的覆盖缺口 | 已完成的迁移清单和评审对话 |
| 提示词与工具描述 | 模型可见的稳定行为和边界 | 内部实现术语与作者推理过程 |
| 诊断信息 | 失败对象、违反的规则、可执行的修正 | “系统正在尝试……”之类执行旁白 |

判断是否需要注释时，可以问一个简单问题：代码和类型已经能否让读者可靠推出这个事实？如果能，注释多半是重复；如果不能，而且误解会导致错误使用，就应写下契约或理由。

## 本地契约与唯一解释并不冲突

“不要重复文档”常被误解为只留一个链接。链接可以承载架构、算法、历史和长篇理由，却不能替代调用点所需的最小契约。

例如销毁方法旁仍应写明：

> 销毁会中止运行，并等待 provider 完全静止。

随后再链接到生命周期设计，解释所有权和竞态处理。调用者无需跳转就能知道完成保证，复杂理由则只有一个权威来源。

适合本地重复的是必要行为；不适合重复的是长篇推导和背景故事。

## 先修改所有者，再更新派生产物

Agent 仓库经常从源码生成工具目录、类型参考、快照或双语页面。直接修改生成文件，会在下一次生成时丢失，也会制造两个真相来源。

更新顺序应是：

```text
识别事实的所有者
  → 修改源码 JSDoc、模板或配置
  → 重新生成目录、快照或镜像页面
  → 检查派生片段能否独立成立
```

尤其要注意“只抽取第一句”的生成器。源文档的第一句必须在离开上下文后仍是完整命题，不能只写“审批请求与策略服务”这种标题式片段。

## 模型可见文字就是行为

工具说明、错误结果、CLI 输出和 prompt 不是普通文案。改一个动词可能改变模型是否调用工具，改一个错误提示可能改变模型是否重试。

这类改动应像接口变化一样处理：

- 找到文字的唯一所有者；
- 检查真实渲染结果，而不只看模板；
- 为稳定文本更新快照；
- 为动态行为运行真实入口测试；
- 明确说明没有快照时由什么证据替代。

不要为了“更自然”静默改写模型可见字符串。

## 一个实用的编辑流程

### 1. 确定范围和权威来源

先确认要编辑哪些文件、当前实现是什么、哪些规则来自更高层文档。排除冻结历史、第三方代码和生成产物。

### 2. 枚举命题

把候选段落拆成行为、条件、时机、模态、例外、所有权、失败与后果。没有这一步，删字很容易把“必须迁移”改成“允许保留”。

### 3. 分类处理

对每一段选择一种动作：

- 保留：已是最小完整契约；
- 补充：缺少调用者可见事实；
- 精简：命题完整，但有重复或装饰；
- 重构：事实在错误位置或混合了教程与参考；
- 延后：存在两种都合理、需要领域判断的表达。

### 4. 验证文字对应的行为

用代码、测试和真实输出逐项核对，不凭旧文档自证。提示词和可见字符串还需验证生成结果。

### 5. 运行最窄而充分的门禁

检查链接、生成同步、双语配对、快照和格式。门禁只能发现结构问题，不能替代语义审查。

## 写作检查清单

- 每个重要句子都能指出可验证的行为或约束。
- 行为、条件、时机、模态、例外和失败没有在精简中丢失。
- 注释解释非显然契约，而不是复述控制流。
- 本地保留最小调用契约，长篇理由链接到唯一所有者。
- README 写消费者需要的限制，不充当 TODO 仓库。
- 生成文件从所有者重新生成，没有手工维护副本。
- 模型可见文字按行为变化验证。
- 文档描述当前状态，不夹带临时评审上下文。
- 实际运行的检查与声称的检查一致。

## 可复用的段落模板

当一个 API 涉及生命周期时，可以按下面顺序写：

```text
在 <条件> 下，<主体> 会 <行为>。
该动作发生在 <时机/顺序>，并由 <所有者> 负责 <资源或副作用>。
失败时 <错误可见性>；取消或销毁完成时保证 <完成语义>。
```

模板只帮助检查命题，不应机械填满每个字段。代码已经清楚表达的内容无需再写一次。

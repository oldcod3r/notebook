# Agent 沙箱与最小权限升级

编码 Agent 必须运行命令，但“能运行 shell”不应等于“默认拥有整台机器”。安全路径应该是：先在受限沙箱中执行，只有真实操作被策略拒绝时，才针对同一操作请求一次更宽权限。

关键不只是选择一个 sandbox runner，而是把约束、拒绝识别、审批和重试组成一个无法绕过的协议。

## 沙箱是一条能力 seam

Harness 是 SDK，不应把某个平台的 `bwrap` 或 seatbelt 命令写死进 bash 工具。执行方消费统一的沙箱计划，平台 provider 决定如何实现。

```text
bash tool → sandbox policy → platform runner → subprocess
                         ↘ denial classification
```

同一个部署可以选择不同模式：只读、工作区可写或不受限。会话中的显式模式变化要写入日志，使执行行为和模型看到的策略来自同一状态。

进程内 fs、web 或 todo 工具不经过 `execve`，因此子进程沙箱不能假装覆盖所有工具。跨工具强制需要各能力在自己的真实边界执行策略。

## 先受限执行，再在真实拒绝后升级

最小权限升级不是“模型觉得可能需要权限，所以先申请”。正确流程是：

```text
受限执行
  ├── 成功 → 返回结果
  └── sandbox denial
        → 请求批准同一操作的更宽重试
        ├── 拒绝/无人应答 → 失败关闭
        └── 批准 → 只重试一次
```

只有 runner 明确分类为策略拒绝，才进入审批。命令退出码非零、网络错误、文件不存在或程序自身报错都不能伪装成 sandbox denial。

批准也不是把会话永久切到不受限模式，而是针对同一解析后操作的一次性升级。重试参数必须与首次调用匹配，避免模型借审批结果换成另一条更危险命令。

## 为什么拒绝后不能只让模型放弃

没有升级路径的沙箱会迫使部署者在两种坏选择中二选一：要么 Agent 经常卡死，要么全局改成危险权限，让沙箱失去意义。

一次性升级提供中间道路：常见工作保持受限，确实越界的操作由人类在看到具体命令、目录和理由后判断。

## Runner 失败与策略拒绝要分开

首选 runner 在容器或受限主机上可能不可用。`bwrap` 缺失、user namespace 被禁用、LSM 拒绝 mount，属于基础设施能力问题，不是本次命令被策略拒绝。

Provider 可以按平台维护后端链并随 SDK 交付 fallback，但必须区分：

| 结果 | 含义 | 是否请求批准 |
|---|---|---|
| 命令违反已生效策略 | 操作越过允许范围 | 可以 |
| runner 无法启动 | 沙箱基础设施不可用 | 不可以，按部署策略失败或 fallback |
| 命令自身失败 | 程序返回错误 | 不可以 |
| 调用已取消 | 所有者不再需要结果 | 不可以 |

把 runner 故障当成权限拒绝，会诱导用户批准一个根本无法通过授权修复的问题。

## 权限状态必须是会话事实

部署默认值可以不写日志；一旦用户或宿主显式切换模式，就应追加会话事件。这样恢复、fork 和调试都能回答某次命令实际处于什么策略下。

Subagent 委派时会捕获父级已经显式授予的沙箱覆盖，但 child 的审批策略固定为 `never`。Child 可以在既有范围内工作，却不能弹出无人负责的升级请求。

这体现了一条可迁移原则：**授权范围可以委派，授权权力不能隐式委派。**

## 沙箱模式不等于安全等级标签

`workspace-write` 只描述文件能力的一部分。网络、环境变量、进程继承、设备、系统调用和进程内工具仍可能有独立边界。

因此不要把模式名写成笼统的“安全/不安全”。策略应该说明：

- 哪些路径可读、可写；
- 网络是否可用；
- 子进程环境如何清洗；
- 哪些工具不受该 runner 覆盖；
- 升级后扩大了哪一项能力。

## 一个安全的升级请求应包含什么

审批方至少需要看到：

- 被拒绝的规范化操作；
- 当前沙箱模式；
- 请求扩大的具体范围；
- 为什么任务需要它；
- 是否为一次性重试；
- 取消或无人应答时的行为。

不要只问“允许更高权限吗”。缺少操作和范围的批准无法审计，也容易让人习惯性点击允许。

## 落地测试矩阵

- 受限范围内命令一次成功，不触发审批。
- 真实策略拒绝产生一条审批，并在拒绝时失败关闭。
- 批准后只重试原操作一次。
- 非策略错误不触发升级。
- 首次调用取消后不再请求批准。
- 重试期间取消能停止工作。
- Runner 不可用走基础设施错误或明确 fallback。
- 会话恢复后策略与日志一致。
- Child 继承范围但无法申请升级。
- 进程内工具不会被错误声称受到子进程沙箱保护。
